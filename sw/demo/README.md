# 2600 demo program (spec §9 item 3)

Our own Atari 2600 program, written by Homer for this repo. No commercial ROM, no code copied from other programs (rule 9).
It shows a title screen in the playfield ("2600", twice across, one colour per row), two players, a ball bouncing left and right, and a tone (an 8-note melody, with a high blip each time the ball bounces).

**Status:** source and cycle proof only. The full-system model (`a2600`) does not exist yet, so nothing has been run and no frame or WAV exists. How it looks and sounds is unchecked. The frames and the WAV come in a later issue.

## Build
```
python3 sw/demo/build.py
```
- **Assembler: the repo's own `tests/core/asm6502.py`**, not dasm. It accepts documented opcodes only and covers everything the demo needs. `build.py` adds what it lacks: `NAME = value` equates (substituted before assembling) and the data tables (`sprite`, playfield, colour and note tables are generated by `build.py` from small Python descriptions: a 3×5 font, two 8×8 glyphs).
- Output: `demo.bin` (4096 bytes, loads at `$F000`, reset vector `$FFFC` → `start`), `demo.sha256`, `demo.lst` (address, bytes, cycles, source), `logs/demo-cycles.log`.
- Reproducible: the build has no timestamps. Two runs give the same hash.
- **sha256 of `demo.bin`:** `cddb8439a2c089f860a671fc271428a19322c01478712a00fa0130e6fbf78c31`
- `build.py` exits non-zero if a check below fails.

## Frame
3 VSYNC + 37 VBLANK + 192 visible + 30 overscan = 262 lines (SPG pp.4–5). VSYNC is timed with WSYNC; VBLANK (TIM64T = 44) and overscan (TIM64T = 36) with the RIOT timer TIM64T, polled through INTIM and closed with a WSYNC (SPG p.12).
Objects are positioned in VBLANK with a WSYNC + 15-pixel divide loop + HMOVE.

The visible area is 24 bands of 8 lines. Line 0 of a band is blanked (VBLANK on): it loads the band's playfield and colours, and shows as a thin black rule. Lines 1–7 draw the players and the ball.

## Cycle check (`logs/demo-cycles.log`)
The script walks every path of the kernel from the instruction after each `STA WSYNC` to the next `STA WSYNC`, taking both sides of every branch, with page crossings assumed worst-case:
- **Worst visible-line path: 60 cycles of 76** (the band setup line; sprite lines 42).
- Deadlines (`@by N` comments in `demo.asm`): VBLANK writes by cycle 22 (before the first visible colour clock, 68 = cycle 22.7), GRP0/GRP1/ENABL by cycle 36, so the players and the ball must start at pixel ≥ 44 (the ball bounces between 38 and 136; the log shows its write at cycle 32 ≤ 36).
- Timer windows: the poll loops leave on the first read of 0, which spec §7.2 puts at pulse (N−1)·64 + 1 after the write (not at underflow). That plus up to 7 for the poll loop falls in the last line of each section (VBLANK line 37, overscan line 30), with margins of 26/42 cycles (VBLANK) and 54/14 cycles (overscan) to the line edges.

Limits of the check: it counts cycles from the listing, it does not simulate. The WSYNC release phase is taken as ±a few cycles; the smallest timer margin is 14 cycles. The real proof is the line count and picture from the `a2600` run, later.

## Opcodes
Documented 6502 opcodes only: the assembler refuses anything else.
